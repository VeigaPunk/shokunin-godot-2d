## Finding A (observation) — `.uid` values are deterministic, not random, and are seeded by `config/name`

Companion `.gd.uid` files are generated by an editor import pass
(`godot --headless --editor --quit --path proj`, exit 0; then `ls proj/*.uid | wc -l` → 82).
Three roots with **identical source bytes** (`camera_follow.gd` sha256 `04a7403e1a93…d7c2d90`),
different `config/name`:

```
runD  name=MechanicOneShotTest      camera_follow.gd.uid = uid://cpt8ajmloovv7
E1    name=MechanicOneShotTest      camera_follow.gd.uid = uid://cpt8ajmloovv7  (/var/tmp/r104-E1/proj)
runG  name=MechanicOneShotTest-w07  camera_follow.gd.uid = uid://lfo6jrfcnij8
runF  name=MechanicOneShotTest-w07b camera_follow.gd.uid = uid://6rijok7ankwv
content unchanged (runH): uid://cpt8ajmloovv7   |  content CHANGED (runI): uid://8oygw0o77pd2
same path (runJ): uid://cpt8ajmloovv7           |  RENAMED (runK): uid://b78yy2twvogtg  (content sha runJ==runK)
repeat staging (runL): uid://cpt8ajmloovv7      # third independent agreement
```

E1's root and my `runD` are **independent staging events in different scratch roots** and
agree byte-for-byte (`uid://cpt8ajmloovv7`) — the cross-root reproducibility claim. The
same row set shows name, content, and path are each independent inputs (each single-variable
delta flips the value with the others held fixed).

**Observation:** the `.gd.uid` value is a pure function of (project `config/name`,
resource path, resource content bytes) on this engine build; reproducible across processes
and scratch roots, *not* process-random. **Inference:** the derivation is a hash over those
three inputs; the *exact* function is not recoverable from these observations. **Unknown:**
whether `.tscn`/`.tres` companions behave the same, and whether the seed includes project
*path* or only the name string (the `.import` case is Finding F; the `create_id_for_path`
case is §Cross-check).

**Consequence for the lane (inference):** any fixture that asserts a literal `uid://…`
string, a literal `create_id_for_path` int, or that hashes a `.uid` file, is **not
byte-stable under the battery's per-run `config/name` rename**. Receipts must bind the
*relationship* (`text_to_id(.uid text) == ResourceLoader.get_resource_uid(path)`), never
the literal. My `custfile`/`nouid` arms are written that way.

## Finding E (observation) — load-cache identity and `cache_mode` busting

```
$ ... --arm=cache
PASS res_uid_w07 cache save=0 same_default=1 same_ignore=0 same_reuse=1 same_replace=1 same_after_replace=1
PASS res_uid_w07 cache uid=-1 uid_text=uid://<invalid> id_path= id_path_is_user=0
$ ... --arm=cachebust          # 2-color file on disk overwritten with a 3-color file
PASS res_uid_w07 cachebust on_disk=3 first_load=2 cached_load=2 ignore_load=3 replace_load=3 after_replace=3 ignore_is_cached=0 replace_is_cached=1
```

- Default load and `CACHE_MODE_REUSE` return the **same instance** (`is_same` true);
  `CACHE_MODE_IGNORE` returns a **distinct** instance.
- `CACHE_MODE_REPLACE` returns an instance that **is** the cached one (`replace_is_cached=1`)
  but whose content is the **new** on-disk state (`replace_load=3`), and the cache then
  serves the new content to a subsequent default load (`after_replace=3`). So REPLACE
  rebinds the path to freshly-read content rather than handing back a separate object.
- `ResourceSaver.save()` to a **`user://`** path leaves `get_resource_uid` = **-1**
  (`uid=-1`, `id_path=""`): user-space resources acquire no UID — a real **coverage** row
  (the exported/`res://` case has a UID, the `user://` case does not).
- Engine diagnostic: `ERROR: Invalid UID. at: get_id_path (core/io/resource_uid.cpp:196)` —
  `get_id_path(-1)` is an **error-emitting** call, not a silent empty return.

## Cross-process persistence (observation) — `add_id` is in-memory only

```
before add_id: sha=40c4886c5b5476c2 size=2965
PASS res_uid_w07 persist_a save=0 uid_before=-1 uid_text=uid://<invalid> add_ok=1 path_of=user://w07/persist.tres cache_bytes=2965
after  add_id: sha=40c4886c5b5476c2 size=2965
CACHE UNCHANGED BY add_id
--- persist_b in fresh process ---
PASS res_uid_w07 persist_b has=0 path_of= uid_now=-1 uid_text=uid://<invalid> cache_bytes=2965
```

`ResourceUID.add_id(id, path)` succeeds **in-process** (`get_id_path` returns the path) but
does **not** mutate `.godot/uid_cache.bin` (sha and size identical before/after), and the
registration is **gone in a fresh process** (`has_id=0`, `get_id_path` empty, plus
`ERROR: Unrecognized UID`). **Observation:** runtime `add_id` is process-local; the
persistent cache is written by the **editor import** path, not by the runtime API. This
**corrects** `r104-E0-spec.md`'s `persist` row ("nested `--import` child then reader child;
uid survives") and `r104-E4.md`'s process-A/process-B plan: a UID *survives across
processes only if the editor import wrote it* (a `.uid` companion or the cache), not
because a runtime `add_id` persisted. E1's `pathtouid` arm independently agrees
(`sidecar_honoured=false sidecar_get_resource_uid=-1`) — a hand-written `.uid` sidecar is
an editor artifact, and the runtime authority is the cache.
