## 3. `s09` — the flake class that constrains tuple measurement

Independent finding, arrived at before S2's §5 was published, and it corroborates S2 §4's
`s09` row ("PASS varies") from the other direction.

**25 runs of `export_prod_s09.gd --arm=census` → 9 green, 16 failed.** Five distinct failure modes
(counted from my `/var/tmp/r104-ver6/s09-*.out`, digits normalised):

```
7  ASSERTION FAILED: pack too small: N bytes
3  ASSERTION FAILED: pack magic mismatch
2  ASSERTION FAILED: export attempt N rc=N chars=N savepack=false tail=[ N% update_scripts_classes
2  ASSERTION FAILED: census mismatch: entries=N, dot_n=N, remap=[N, N, N], paths=[…]
2  ASSERTION FAILED: census mismatch: entries=N, dot_n=N, remap=[N, N, N, N], paths=[…]
```

**Mechanism (OBSERVATION, then INFERENCE).** `export_prod_s09.gd:34` is
`const ROOT_NAME := "r101_export_prod_s09"` and `:169` is
`_root = OS.get_temp_dir().path_join(ROOT_NAME)` — a **fixed, process-global, unparameterised**
path. The fixture ignores `--work=`/`--root=` entirely (`:161-164` parses only `--arm=`), and
`OS.get_temp_dir()` **ignores `TMPDIR`**: three distinct private `TMPDIR`s I set
(`/var/tmp/r104-ver6/tmp`, `…/tmp2`, `…/iso/tmp`) all stayed **empty** while the shared
`/tmp/r101_export_prod_s09` kept being rewritten. Proof:

```
$ ls -la /var/tmp/r104-ver6/tmp2      → total 0   (empty after 6 runs with TMPDIR=$W/tmp2)
$ ls -la /tmp/r101_export_prod_s09/   → nested/  out/   (live, mtime = latest run)
```

**Concurrent-run test (3 simultaneous `--arm=census`):** all three `rc=2`, all three identical
`census mismatch: entries=11, dot_n=2, remap=[39, 4…]` — i.e. all three read each other's
half-deleted `$TMPDIR/r101_export_prod_s09`, since `_rm_rf(_root)` (`:173`) deletes the tree at
startup while `_export_until_usable()` re-exports into it.

Cross-seat corroboration that this bites *other* seats: S1's parallel batch
(`/var/tmp/r104-S1-COMPANION-DISPOSITION/out/export_prod_s09.txt`) failed with
`census mismatch: entries=15, deep3=5, gdc=[123, 190, 210, 665] …` — **entries=15 is the
`sensitivity` arm's expected census**, appearing inside a default run. Two arms shared one root.
S2's own scratch shows the same class: `s09.out` GREEN, `s09-census.out` and `s09-run.out` both
`pack too small: 0 bytes`.

**Second, distinct defect — the retry loop cannot retry.** `_export_until_usable()` (`:236-257`)
is explicitly written to re-export up to `MAX_EXPORTS=3` while `project.binary` is empty (E9's
M5), but `_census()` `_fail()`s *and returns* on exactly the two shapes it must survive:
`pack too small` (`:264-266`) and `pack magic mismatch` (`:267-269`). So a transient first-export
artifact aborts the whole row instead of retrying. I patched a scratch copy to `return {}` there
plus `continue` at the call site — **3 green / 3 fail** (`census mismatch: entries=11`,
`entries=12`, `pbin_size=0`). Repair is necessary but **not sufficient**: the global-root
collision still dominates. *(A first, naive form of this patch — `return {}` without `continue` —
left the SceneTree with nothing calling `quit()`, and the row hung to `rc=124`. Recorded because
it is the shape a careless repair would take.)*

**Consequence for the orchestrator (INFERENCE).** `s09`'s pinned prefix
(`PASS export_prod_s09 census entries=13 deep3=3 deep2=2 gdc=[190,210,665] remap=[39,45,49,97,103] pbin_ok=1`)
is byte-stable in every green run — `sha256(prefix, no trailing newline)` = `7771df92970d5c02`
across 5 of my runs **and** S2's `s09.out`; with the newline retained the same five files all
give `6ca3ab1f802e601b` — but the row is **only conditionally registrable**: `s09` must be the sole consumer of
`$TMPDIR/r101_export_prod_s09` at that moment. It is safe inside the serial battery; it is not
safe under any parallel replay. Its `pck_sha256=` varies in **8/8** green runs (8 distinct
values), which S2's pin correctly truncates before.

## 4. The one DIVERGED tuple: `export_prod_s11_pack`

S2 §5 pins the pack sha and §5.3 states it is "**byte-stable x4** (`abd696827f86a96b…` all four)
— the pin keeps it, and it is safe", and lists as **UNKNOWN** why `s11`'s sha is stable while
`s09`'s is not. Both halves of that are wrong, and the mechanism is readable in the source.

**Evidence.**

```
$ # my scratch (project name "MechanicOneShotTest", user:// root, 3 reps)
  PASS export_prod_s11 pack … sha256=b3cd4fb013aca12bdbacf2030ec55c37f3bc7ba2bb7da84d2cf1862317837e5b …   ×3 identical

$ # root overridden via the fixture's own R101_E11_ROOT, 3 reps
  sha256=bb7cf5fe1e0b87663d07705edcb90083963bac4870dcb850121e41b09b6f6f85                                     ×3 identical

$ # root dir REMOVED before each run (cold root), 5 reps
  cold1 sha256=8e233332549b3c77   cold2 sha256=2e7334f2b0ea3137   cold3 sha256=beb3ecb878eca72f
  cold4 sha256=03c3c11b0fd9d5ef   cold5 sha256=448b97beadd0cd7d        → 5 distinct shas

$ # battery project name "MechanicOneShotTest", cold root, 3 reps
  cold1 sha256=7a33a6f8969b7c20   cold2 sha256=d1c33d267b18662f   cold3 sha256=aa9afdf720513916
```

Four independent root configurations produced **four mutually distinct** stable values, and a cold
root produced a **fresh value on every run** (5/5, and 3/3 under the battery's own project name).
S2's `abd69682…` is not reachable in any of them. `pck_bytes=2008` and every other token in the
line reproduced exactly, so the divergence is confined to the sha token.

**Mechanism (OBSERVATION → INFERENCE).** `export_prod_s11.gd:82-91` resolves its root by a
three-way fallback — `$R101_E11_ROOT`, else a shared root, else
`ProjectSettings.globalize_path("user://r101e11")`. `user://` is keyed on the **host project
name**, so the pack content — and therefore its sha — is a function of the project directory the
fixture happens to be run from. S2 measured in `/var/tmp/r104-S2/scratch` whose
`project.godot:2` is `config/name="MechanicOneShotTest-S2"` (its app_userdata dir
`~/.local/share/godot/app_userdata/MechanicOneShotTest-S2` exists), whereas the battery copies
`corpus/fixtures/` whose name is `MechanicOneShotTest`. **S2's pin therefore cannot hold at
registration.** Additionally, a cold root gets freshly-generated random `.uid` values
(`main.gd.uid: uid://h0twfnc00juo` in my warm root) that the pack embeds, which is why even a
fixed root name gives a new sha per cold start.

This also **resolves S2's stated UNKNOWN**: `s09`'s sha varies because its root is a fixed
*global* path shared with every other process on the host, while `s11`'s is per-project and
therefore stable *only while that project's directory persists*. Neither fixture is "stable";
`s11` just has a narrower collision domain.

**Fix (for the orchestrator, applied as a mutation — not by me).** Truncate the pin before
`sha256=`:

```python
("export_prod_s11_pack", "export_prod_s11.gd", ["--arm=pack"], 0,
 'PASS export_prod_s11 pack magic=GDPC pck_bytes=2008 dircount=7 project_binary_bytes=164 savepack_receipt=true export_rc=0 export_stderr_bytes=0'),
```

This is the same conservative treatment S2 already applies to `s09_census`, and it keeps every
token that is a real property of the pack. If the sha is wanted as a pin, the row must instead fix
the root explicitly (`R101_E11_ROOT` under a serial-only, cleared dir) — that is a harness change,
outside a tuple.
