## 4. Findings — the live control exposes real defects in the landed fixtures

The row-level control (fixture present ⇒ the row's own pin **must** classify `True`) failed on the real registration-shaped rows. Root-caused by direct measurement, not inference.

### 4.0 D-D — `res_uid_s02.gd --arm=xproc_read` is non-idempotent and order-dependent

The sharpest finding. `xproc_read` deliberately tests cross-process persistence, but it is the **only** arm that does not reset the resource it reads, while `xproc_seed` is the only one that calls `_wipe()` (`res_uid_s02.gd:264`). Three runs of the *same command*:

```
run 1 (after a preceding --arm=xproc_seed):
  PASS res_uid_s02 xproc_read fresh_first=v1 same_in_process=true rewrite_reuse=v1 repl=v2
run 2 (immediately after run 1, same scratch tree):
  FAIL res_uid_s02 xproc_read reason=cross_process_or_l5_law_mismatch fresh_first=v2 same_in_process=true rewrite_reuse=v2 repl=v2
in isolation (fresh XDG_DATA_HOME, no seed):
  FAIL res_uid_s02 xproc_read reason=cross_process_or_l5_law_mismatch fresh_first=n same_in_process=true rewrite_reuse=v2 repl=v2
  stderr: ERROR: Cannot open file 'user://res_uid_s02/v1.tres'. (+2 more)
```

Observation: the arm asserts `fresh_first == "v1"`, which only holds if a *previous process* left `user://res_uid_s02/v1.tres` holding v1. Under battery registration each row runs once per battery run against whatever state the tree carries, so this row **cannot be green twice in a row** — it passes on a seeded tree and fails on the second battery run. Label: observation for the three runs above; inference for the "fails on a second battery run" consequence.

The `fixture-row` phase reports it `PASS` because it collects the live PASS line on the seeded tree and only tests that the *dead* capture fails — which is true. That is the correct scope of this seat's claim (harness-dead), and D-D is a **separate** row-hygiene defect that `rows` (the live control) surfaced.

### 4.3 D-C — the drift is cross-run state accumulation, not intrinsic randomness

On a **pristine** project + fresh XDG dir (`.godot/uid_cache.bin` absent, `--import` run once), `custfile` is perfectly stable across 3 runs:

```
import exit=0
run1: uid_cache.bin=2996 | uid_text=uid://covpvxabicy4h | cache_bytes=2996
run2: uid_cache.bin=2996 | uid_text=uid://covpvxabicy4h | cache_bytes=2996
run3: uid_cache.bin=2996 | uid_text=uid://covpvxabicy4h | cache_bytes=2996
camera_follow.gd.uid content: uid://covpvxabicy4h
```

Whereas inside the `rows` scratch tree the same arm reported `uid_cache_bytes=296` in one pass and the pin measured earlier was `uid://b3ance8m3vljl`. The mechanism is confirmed by the corpus itself: `w07` declares `const BASE := "user://w07"` and `DirAccess.make_dir_recursive_absolute(BASE)` (`res_uid_w07.gd:7,40`) but **never cleans it**, and the arms write `.godot/uid_cache.bin` plus `.uid` companions (`:112,218,254`). Each arm run therefore leaves state that the next run reads back.

Observation: `persist_a cache_bytes` grows 2873 → 2965 (one extra record ≈ 92 B) purely from re-running. Label for the consequence: **inference** — under battery registration these pins will drift as the cache accumulates, so an arm that is green at registration time will not be green on a later run.

### 4.4 Consequence for registration (the reason this seat's proof matters)

A `res_uid_w07` row registered today with `expected_exit=0`, the live PASS line as signature, and arity 5 (`allowed_errors=[]`) will classify **FAIL** immediately: `signature in output` holds, but `unrelated_errors` is non-empty. Registration therefore needs, per arm, (i) an `allowed_errors` tuple carrying that arm's deterministic refusal lines, and (ii) a pin whose varying fields are either normalised away or split into a second row — exactly the F1/F2 discipline r103's `mut05_gate` had to adopt for the same reason.

1. **The harness-dead class is closed for res_uid**: 44/44 landed arms + 2 synthetic + 1 absent = **47/47 rejected**, every one with a `True` live control. `mut05.py` is the reusable driver; no further edit needed.
2. **`rows` cannot run against the repo battery until the `res_uid*` CASES splice lands** (`NO_ROWS`, `cases_total=552`). The recipe is in `rows.json`; after the splice, `setup && rows` is the whole check.
