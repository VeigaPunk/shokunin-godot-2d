## 6. Mechanism: why a built artifact's sha256 is not reproducible

Controlled 3-arm experiment, `/var/tmp/r104-W9/pcksha.py`, scratch `/var/tmp/r104-W9/pcksha`
(6 real `godot --headless --export-pack` calls, no battery):

| arm | protocol | PCK sha256 | identical |
|---|---|---|---|
| SAME | two exports from **one** project dir (stable `.godot`) | `f3d3034251e66a96…` ×2 | **True** |
| FRESH | two exports from **two freshly-built** project dirs | `a83fdf76d773cc90…` vs `350a1d5f40095665…` | **False** |
| REGEN | same dir, `rm -rf .godot` between exports | `64c93e0e78e3cc91…` vs `8c7751f71e903cd8…` | **False** |

Entry-level diff of the FRESH pair (`/var/tmp/r104-W9/entrydiff.py`): both 1732 B; **exactly 20
differing byte positions in 2 ranges** —
`[811,814]` (4 B, A `2d4944e7` / B `c17bb7cd`) and `[1300,1315]` (16 B, an entry MD5).
This is the r103-w9 finding reproduced independently: the 4-byte per-`.godot`-scan word plus the
MD5 that covers it. The packer's `.scn`/`project.binary` entries carry first-scan state, so the
container hash is a function of the cache, not of the source.

This is why the battery's own `export_prod_det_a` (which builds a fresh project each run) prints a
different artifact sha every run — and why `export_prod_det_b`'s intra-run comparison
(`equal_to_sample1=true byte_diff_count=0`) still holds: within one run both samples share the cache.

## 7. PROTOCOL (deliverable) — byte-stability rules for r104 official runs

**Rule P1 — the official byte-stability artifact is the verdict tuple, not the file.**
Canonical form:
`sha256(json.dumps([(case, verdict, actual_exit, expected_exit, signature) for r in results], sort_keys=True, indent=2))`
Measured: PASS-554 pair IDENTICAL, PASS-571 pair IDENTICAL, both real-change pairs differ.
`verdicts.json` itself is **never** byte-comparable across runs (the run-id is in `scratch`, `command`
and `artifact`).

**Rule P2 — a pin may carry a hash only of a tracked source file or a name-table digest; never of a
built artifact.** Source hashes are stable (8/8 for `r95b_order.gd`, `export_prod.gd`, …). Built
artifacts are not (§6), and even their *size* drifts by 1 B (`zip_bytes=1800`/`1799`,
`bytes=3982`/`3983`).

**Rule P3 — pins must stop before `output` fields fed by per-process randomness.** Named
never-pinnable classes measured this seat: `ResourceUID` counter values (`uid_c=`, `id=N_xxxxx`,
`sample=…`), random multiplayer peer UIDs (`raw_uid=`), `proc=`/`pf=` tick counts, `*_at` /
`*_seconds` floats, and ASLR pointers in crash backtraces. The existing 552 pins already obey this
(§5) — the rule records *why*, so r104+ rows keep obeying it.

**Rule P4 — a receipt-shape gate may not flag these.** Any r104 gate extension (C2's tab-PASS work,
C3's evasion probe) must not treat a volatile-class token as a receipt-shape violation, or it will
flag every run. The r103 `receipt_shape_audit` (`run_battery.py:1998-2020`) is already scoped to
grammar rows, which is the right boundary.

**Rule P5 — cross-run comparison needs the run-id and host-path masks** (§3 S2) plus the code-state
check: compare `sha256(run_dir/scratch/<fixture>)` before comparing receipts (§2). Two runs that
differ in a fixture sha are a code change, not a stability failure — this is exactly the
`r101_ytrans_census` case.

- **Bounded**: this is a protocol over *stored artifacts on this host*; it makes no claim about
  engine determinism in general, about non-headless runs, or about platforms other than
  `arch_linux`.
