## 2. Replay shape (from source only)

`_run()` iterates `['census','routing','hover','motion','localpos','cursor','clip',
'drag','touch','subvp','warp','focus','render','osmeta']` (`r100b_seq.gd:83-125`).
With `--clean=1`, `_cleanup()` frees root children + `_nodes` after each cell;
with `--clean=0` the whole tree persists. Cells 1–7 are therefore:
1 `census`, 2 `routing`, 3 `hover`, 4 `motion`, 5 `localpos`, 6 `cursor`, 7 `clip`.

Singleton facts the fixture itself establishes (and the landed pins corroborate):
- `root.push_input(...)` does **not** update `Input`/Viewport singleton state:
  fresh `r100_gui_cursor` keeps `(0,0)` across `c1_push_mm`/`c2_push_mb`, and
  fresh `r100_gui_routing` prints `s10_input_state held_push=0 cursor=(0.0, 0.0)`.
- `Input.parse_input_event(e)` + `await process_frame` **does**: cursor follows
  `global_position` (`c5_gpos_drives=(60.0, 60.0)` for pos (70,70)/gpos (60,60));
  a parsed `ScreenTouch` press drives the emulated mouse cursor/button
  (`c6_parse_st=(44.0, 44.0)`, `r100b_emul` `held=1 cursor=(44.0, 44.0)`).
- GUI picking: later siblings win (hover `h3=B` despite `A`/`P` covering the same
  point in the noclean tree); `MOUSE_FILTER_IGNORE` skips the control but still
  recurses into children (hover `h5=C` under `I`); a held-button focus captures
  motions (see §5).

Mechanisms (cells 3–7) — [M] unless marked:
- **hover h0=P**: routing's `P` sink survives (no cleanup) and remains the
  stored hovered control (`r100b_seq.gd:280-299` leaves `P` hovered; `P` is
  freed only in the clean variant, where `h0=null`). All eight `ev` transitions
  are unchanged: the hover cell's own `A`/`B` are later siblings added on top.
- **motion m1/m2/m3 empty**: routing's `s9_rb` (`:302-310`) pushes a RIGHT press
  that is never released, leaving a sticky viewport mouse-focus on `P`. While a
  focus is held, **motions are delivered to the focus, not the control under the
  cursor**, while the hovered control is still position-derived. Directly
  instrumented (scratch copy `v5`, `--clean=0`): after `m1`,
  `P`'s log ends with `P:mm(bm=0,pos=10.0,10.0,…,rel=5.0,7.0,…)` and
  `hovered=S` — so `S.log` stays empty and `m1[-]`. `m4` reads only singleton
  state, which the pushes never touched (`held=0 cursor=(0.0,0.0) vel=(0.0,0.0)`).
- **localpos first push `c[-]`**: same sticky focus. Instrumented: after push 1
  the (unprinted) routing `P` log gains `P:mb(b=1,p=1,…,pos=30.0,14.0)`;
  after push 2 the cell's own `C` gains
  `C:mb(b=1,p=1,…,pos=6.0,2.0,gpos=30.0,14.0)`. `loc_c=-24.0,-12.0` proves the
  viewport cursor is still `(0,0)` at that point (pushes never move it). The
  exact engine-internal rule that ends the sticky focus between the two pushes
  is [U]; it does not affect any printed token.
- **cursor (cells 6, both variants)**: as in §3.
- **clip `(90,4)`**: the clip cell's own `ED` (origin `(60,0)`, so local
  `(30,4)`) records the press and `FA` (topmost at `(90,4)`, `(80..112)`) records
  nothing. Instrumented: after the 62/90 presses, `ED`'s last entry is the
  `gpos=90.0,4.0` press and the sticky routing focus no longer receives events.
  Note this is **not** a leftover sink (there is no earlier `ED` in the process);
  the boundary report's "clip's `(90,4)` press lands on a leftover `ED`" wording
  (`r100-boundary.md` §8) is imprecise — it is the clip cell's own `ED`.

## 5. Discrimination / bisection (why the claimed causes are the real ones)

Scratch copies of the fixture, each run `--clean=0` (rc=0 each):

- `v1` — add the missing RIGHT release after routing `s9`: motion `m1/m2/m3`
  revert to the fresh values, localpos push 1 reaches `C`, and clip `(90,4)`
  returns to `FA`; hover `h0=P` and cursor stay diverged. ⇒ the un-released
  right press is the **sole** cause of the motion/localpos/clip leaks.
- `v2` — add a release after the cursor cell's parsed touch press: cells 1–7
  unchanged except every clip press is now lost (`ed=-`, `fa=-`); ⇒ the cursor
  cell's un-released parsed touch is a second live singleton leak, but it does
  not drive any cell 1–7 divergence.
- `v3` — both edits: behaves like `v1` (hover/cursor still noclean-diverged).
