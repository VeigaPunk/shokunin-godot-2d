## What scenario 08 pins

Godot resolves Linux export templates as
`$XDG_DATA_HOME/godot/export_templates/<version>/` (else `$HOME/.local/share/...`).
Binary strings confirm both tokens:
`strings /usr/bin/godot | grep -i 'export_templates|XDG_DATA'` →
`XDG_DATA_HOME`, `export_templates`, `No export template found at the expected path:`.
`godot --help` exposes **no** templates-dir flag (only the `--export-*` modes), so
the override lever is the child's `XDG_DATA_HOME`.

Scenario 08's question — "error class **or** fallback?" — answers **both**,
depending on export mode, measured (not assumed):

* executable targets (`--export-release` / `--export-debug`) → **error class**:
  rc=1, configuration errors, zero products;
* data-pack targets (`--export-pack`) → **fallback**: rc=0, pack written without
  any template (PCK and ZIP both);
* `--export-release` aimed at a `.pck` path still **fails** — the export mode,
  not the target extension, decides the template requirement.

## Discriminations (what a forgery would have to fake)

* `control_exe`: rc + a 73,519,416-byte ELF at the export path + sidecar GDPC —
  printing a receipt without exporting fails the in-fixture stat/magic asserts.
* `missing_exe`/`missing_debug`/`missing_relpck`: rc=1 **and** zero products
  **and** both template paths echoed *under the per-run override dir* **and**
  both exact ERROR lines. A generic failure (bad project, bad preset) would have
  to reproduce all four simultaneously.
* `missing_pack`: rc=0 + GDPC + no template-error line — this is the fallback
  arm; it fails if the override stops mattering (e.g. templates get embedded
  into pack export).
* `missing_zip`: weaker by construction (transient zero-size observed); treated
  as observation, not a hard invariant.

## Observation vs inference vs unknown

* **Observed** (commands + bytes above): refusal class and rc=1 for executable
  release/debug and release-to-`.pck`; rc=0 fallback for pack exports (PCK/ZIP);
  control exe byte-identical to the installed template; symlink override proves
  the templates path is the lever.
* **Inference**: the template requirement is decided by the export *mode*
  (`--export-release/--export-debug` vs `--export-pack`), since a `.pck` target
  still refuses under release mode; and template lookup sits under the XDG data
  dir (§ strings + path echoed in the error).
* **Unknown**: cause of the one 0-byte zip artifact (not reproduced in three
  later runs); whether another supported override lever exists for the
  templates dir (none found in `--help`/strings).
