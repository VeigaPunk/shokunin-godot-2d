## Ground truth: PCK format v4 as produced by 4.7.2 (measured, all md5-verified)

Header, little endian, from `xxd` + python parse of `out/game.pck`:
```
0x00 u32 magic "GDPC" (47445043)
0x04 u32 pack format version = 4
0x08 u32 ver_major=4  0x0C ver_minor=7  0x10 ver_patch=2
0x14 u32 pack_flags = 2 (PACK_REL_FILEBASE)
0x18 u64 file_base = 0x70   <- data region starts here (first file's bytes)
0x20 u64 table_offset = 0x9d0/0xa00/…  <- NEW in v4; file table lives AFTER data
0x28..0x6F 48 zero bytes, then data from file_base
@table_offset: u32 file_count, then per file:
    u32 path_len (already 4-byte aligned, NUL padding included)
    bytes path (NO "res://" prefix)
    u64 offset (relative to file_base), u64 size, 16B md5, u32 flags
```
Every one of the 10 md5s recomputed from raw bytes matched (`md5_all_ok=true`), which is what validates this layout reading. Reading the path bytes must drop trailing NULs *before* decoding (`get_string_from_ascii()` on NUL-padded bytes emits Godot's "Unicode parsing error: Unexpected NUL character" warning).

### Icon rows
- **Triple present**: source `icon.svg` (166 B, equal to the on-disk source), `icon.svg.import`, and the imported texture `.godot/imported/icon.svg-218a8f2b3041327d8a5756f3a245f83b.ctex` (686 B). The ctex path is not hardcoded: it is read out of the `.import` file's `path="…"` line and looked up in the pack, so a differing import hash still resolves.
- ctex bytes begin `GST2` (47535432) and size > 600 — pinned as bounds, not literals, because the ctex is compressed and its exact size is importer-dependent.
- Settings tie-in: `application/config/icon` in the written `project.godot` is `res://icon.svg`, and that path is present in the pack.

### `.uid` census rows (the core claim)
- **`uid_sidecar_packed count=0`** — no pack entry ends in `.uid`; the only path containing "uid" is `res://.godot/uid_cache.bin`.
- `probe_actor.gd.uid` **exists on disk** (20 B, text `uid://2o1qe0dm228n`) and is still not packed → the absence is a real exclusion, not a missing source file.
- `icon.svg.uid` does not exist on disk (imported resources keep their UID in `.import` instead) — also pinned.
- **Transit path**: `uid_cache.bin` (62 B) parses as u32 count=2 then per entry u64 UID (little endian) + u32 exact path length + path: `res://icon.svg`, `res://probe_actor.gd`. Both UIDs equal `ResourceUID.text_to_id()` of the text carriers (`.import` for the icon, `.gd.uid` for the script) — cross-consistency, since Godot mints fresh random UIDs per project (observed: icon `uid://40bef2gfjj5r` → `uid://cuoje3c1xqlev` → `uid://2833476408765231168` across runs).
- `uid_cache.bin` in the pack is **byte-identical** (sha256 `f9f754b1…`/`574b29f6…` per run) to the on-disk `.godot/uid_cache.bin`.
- Script UID byte search over the whole pack: 2 occurrences, little-endian only, located in `uid_cache.bin(1)` and the compiled main scene `…-main.scn(1)`; `be_occ=0`, `in_gdc=0`. So the `.gdc` does **not** carry the UID; the pack references the script by UID from the scene and from the cache.

### Independent-reader / forgery rows
- **zip cross-reader**: `--export-pack` with a `.zip` output path yields the same 10 entries; `ZIPReader.get_files()` (names without `res://`) matches the PCK path set and each entry's bytes match by sha256 (`zip_census entries=10 paths_match=true bytes_match=true`). Two independent readers agreeing is the anchor, not the same parser twice.
- **Forgery controls** (in-process, all rejected): census with the icon `.import` entry removed; census with a forged `res://probe_actor.gd.uid` entry added; census with `uid_cache.bin` size +1; census with the uid cache emptied. The verifier additionally recomputes the cache's byte size from its parsed content (4 + Σ(12 + len(path))), which is what rejects the size mutation; the same census verifier accepts the true census (`forgery:baseline ok`), so the rejections are not vacuous.

## Generalization probe (out of fixture, `/tmp/r101-E10/pristine`, 3 scripts, `helper.gd` with `class_name` + `tools/helper_tool.gd`)
- All three `.gd.uid` sidecars exist on disk; pack `file_count=14` and **`uid entries: []`** — still zero `.uid` entries.

## Observation vs inference vs unknown
- **Observed** (raw bytes/exit codes this round): all sizes, md5s, sha256s, the zero-`.uid` census, the 2-entry cache and its byte-identity, the `.gdc`/`.remap` substitution, zip/PCK agreement, forgery rejections, exit codes 0/1.
- **Inference** (not separately proven): that the `.scn` occurrence of the script UID is the scene's ext_resource reference (I matched byte patterns only); that `.uid` exclusion is intentional engine policy rather than 4.7.2-specific behavior (only 4.7.2 was measured).
- **Unknown**: whether a *non-script* `.uid` (e.g. a `.tres` custom resource UID) can ever surface as a pack entry — untested; behavior under `export_filter=resources/exclude_filter` variants is E6/E7 scope; `--main-pack` launch receipts are E4/E1 scope.
