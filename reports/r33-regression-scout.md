# Round 33 regression scout — prior UI controls and battery caveats

Read-only review of the proposed CheckBox press/release-depth move, current fixture/runner, and prior named-verifier reports. I ran no engine or battery command and changed no fixture or runner. This report is my only artifact.

## Prior UI baseline and proposed depth distinction

The current `checkbox_toggle.gd` creates a focused, initially unchecked CheckBox and a `Ready` Label. It connects `toggled(bool)` in the positive arm, then sends two `root.push_input(ui_accept)` press/release pairs, awaiting a frame after each edge. Assertions currently occur only after each complete pair: connected expects state true/false, receipts `[true,false]`, and Label On/Off; disconnected expects the two state changes with no receipts and Ready, then exits at the intended final missing-signal diagnostic. It does not currently assert state, receipt count, or Label immediately after either press edge. The proposed press-only unchanged-state assertions followed by release-only next-state assertions would therefore add edge-specific depth rather than a new control type or signal-coverage category.

The r32 named verifier report records a full default-path replay of **56/56 aggregate PASS = 45 ordinary + 2 mutants + 9 opt-in/probe records**. Its comparison to the r31 raw receipt says all 54 predecessor `(case, verdict, actual_exit, signature)` tuples matched; the two added CheckBox rows are connected PASS/exit 0 and disconnected expected-negative PASS/actual exit 2. Its direct Godot runs observed both connected transitions and both disconnected state transitions; those observations are post-pair, not press-only. This is the appropriate prior baseline, not fresh r33 runtime evidence. The existing Button fixture covers press/release observations for `Button.pressed` and Label, but is not itself evidence of CheckBox edge semantics.

For the proposed contrast, both arms should assert after each press that state, signal receipts, and Label still equal the preceding completed-action values; after each release they should assert the next expected state, with connected receipt/Label changes or disconnected no-receipt/Ready behavior. Keep both actions in the disconnected control before its final intentional missing-signal exit, so the expected negative does not hide whether both state transitions happened. A scratch omission of release1 should fail at a specifically identified release1 state assertion after a valid setup and unchanged press1; it is mutation sensitivity evidence, not a substitute for the tracked paired control or full replay. Whether Godot's actual routed input has these precise press-only semantics requires runtime evidence from the assigned executor and named verifier; this read-only review cannot establish it.

## Export, timeout, and fault-injection caveats

The r32 named verifier report says the default-path command included `--probe-export-launch` and `--probe-timeout` and exited 0; these are bounded probe results from that replay, not general export readiness or universal hang/cleanup guarantees. Export-launch is a bounded Linux/X11 scratch export-and-launch check, not cross-platform export validation. Timeout probes classify their bounded child-process scenarios only. The separate r32 `--fault-injection` replay has outer harness PASS with intentional inner FAIL classifications for `fault_hang` (timeout) and `fault_unrelated_error`; `fault_clean_expected_negative` passes. That standalone self-test is not the seeded battery and its inner FAILs must not be described as a clean run or as CheckBox regressions. Any r33 report should distinguish the full default-path replay, fault-injection mode, and any scratch sabotage, and compare the named-verifier raw case map to the r32 baseline while allowing only the explicitly intended CheckBox signature changes.

## Bounded conclusion

The r32 baseline already covers two complete CheckBox toggles and their boolean `toggled`/Label effects, but lacks separate per-edge observations. The proposed edge assertions would deepen this existing synthetic headless `ui_accept` behavior only if named non-author real-Godot replay confirms press-only invariance and release-only transitions, and prior rows remain unchanged. This review makes no new runtime/regression finding. It does not support pointer activation, rendered output, accessibility, physical keyboard/user timing, or production UI claims. No engine/editor or seeded controls were changed; no commit, push, or merge.
