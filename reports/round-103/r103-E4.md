## 2. Measured layout (observation, byte-level; packed format version 4 on 4.7.2)

```
0x00 u32 magic "GDPC" (LE 0x43504447)
0x04 u32 pack_format_version = 4        <- 4.7.2 writes 4, not the 2 of the older notes
0x08 u32 major=4  0x0C u32 minor=7  0x10 u32 patch=2
0x14 u32 pack_flags   bit1 (0x2) rel-filebase (always set here), bit0 (0x1) dir-encrypted
0x18 u64 file_base    data-region start, relative to pack start
0x20 u64 table_ofs    directory offset, relative to pack start
0x28..0x64            60 zero bytes (measured all zero, both arms)
table: u32 count, then records [u32 name_len | name (NUL-padded to name_len) |
       u64 ofs | u64 size | md5[16] | u32 flags]  == 4 + name_len + 36 bytes
       ofs is relative to file_base; every (file_base+ofs) is 16-aligned;
       blobs precede table_ofs and do not overlap (pairwise range test).
embedded trailer: last 12 bytes = u64 pck_size + u32 "GDPC"; pack starts at
       file_size - 12 - pck_size.
```

Two laws the arms *compute* instead of pinning:

- `file_base == 100 + ((16 - ((pck_start + 100) % 16)) % 16)` — the data region is 16-aligned in the *containing file* coordinates. Witnesses: standalone `pck_start=0 -> 112`; embedded `pck_start=73519416 (mod 16 == 8) -> 104`. One expression, two arms.
- `table_end` is 8-aligned in containing-file coordinates, and `table_end + tail == pck_bytes` (standalone tail 0; embedded tail 4 measured).

Rebuttal of the recon guess: E3's `r103-E3_packparse.py` reads `dir_off` as a u64 at 0x20 and has no `file_base` — the extended header actually carries `file_base` at 0x18 *and* `table_ofs` at 0x20, and entry offsets are relative to `file_base`, so its `md5` cross-checks and `pbin_offset` would both be wrong. (Observation about that file's layout assumption; no edit made to it.)

## 5. Divergences the rows exist to catch (observation; interpretation labelled)

1. **Offsets are file_base-relative, not absolute.** Every arm prints `md5_rel=<count>` and `md5_abs=0`: the stored md5[16] matches only when the blob is read at `file_base+ofs`; reading at bare `ofs` matched 0/7 in every artifact. A parser that ignores 0x18 fails all entries. Cross-witness: `main.gdc` sits at ofs 0 (blob `GDSC` at absolute 112) and `project.binary` at ofs 1088 (`ECFG` at absolute 1200).
2. **`file_base` is alignment, not a constant.** 112 standalone, 104 embedded, both produced by the alignment expression from the pack's position.
3. **Dir-encryption flag vs bytes.** `encrypt_pck=true, encrypt_directory=true` writes flags bit0 in both runs, but only the env-key run is ciphertext: keyless records are 468 B plaintext carrying `project.binary`/`uid_cache` markers with md5 7/7 (and differ from the plain pack at exactly byte 20); keyed records are 520 B with neither marker, count still readable as 7 at `table_ofs=1472`.
4. **The project-settings key channel is not an encryption channel** (observation from the hand probe, kept out of the row gates): adding `[editor] script_encryption_key="<64 hex>"` to the child `project.godot` produced `encdir_key.pck` 2056 B with flags=3 and a fully plaintext, md5-valid 7-entry table at `table_ofs=1584`; the only visible effect was `project.binary` growing 269 -> 377 B (the key string baked into it). Same key value delivered via `GODOT_SCRIPT_ENCRYPTION_KEY` at export time did encrypt. Inference: headless CLI export reads the key from the environment, and a project-settings key is merely a normal setting that ends up inside `project.binary`; a consumer must not infer encryption from the flag alone in either direction.
5. **Cold-export entry set is a stable 7-row census** on this child project (`main.gd` + `main.tscn`): project.binary, main.gdc, main.gd.remap, main.tscn.remap, .godot/uid_cache.bin, .godot/global_script_class_cache.cfg, .godot/exported/<uid>/export-<hash>-main.scn. The exported-scene path carries a per-project uid+hash, so the fixture classifies it as `.godot/exported/*-main.scn` rather than pinning it.

## 7. What would falsify these claims (fixture teeth, for critics)

- any entry md5 read at bare `ofs` matching (arm prints `md5_abs`; gate demands 0)
- a `file_base` that is not the alignment expression for the *computed* `pck_start` (embed arm computes it; a hardcoded 104 would not prove anything, and a changed template still passes only if the law holds)
- a table that does not end 8-aligned, blobs out of bounds, overlapping blobs, non-zero entry flags, non-zero 0x28..0x64 pad
- a class set other than the measured 7 (duplicate/dropped/renamed entry)
- keyless EncDir becoming ciphertext, or keyed EncDir staying plaintext / losing the marker-free records region / count becoming unreadable
- a trailer whose magic is not `GDPC` or whose size does not equal the pack length
