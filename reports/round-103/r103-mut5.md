## 2. Account model — and the two calibration defects it had to fix

Reference green runs (both r102, 554 rows, all PASS):
`corpus/live/runs/20261018T212500022987Z/verdicts.json` sha256=`65986c3f…3134c0` (run1) and
`…213443471189Z` sha256=`65e7fae0…a6a5f68` (run2, the one mut05 tampers — mut05 §1 log line
`run=… rows=554`).

Key function (evidence: `mut05_gate.py:31`): `key(line) = ('verb', t0, valnorm(t1), t2k)` for
designed-verb lines (`t0` in the 44-token census or `*_DIAG`), else `('raw', valnorm(t0))`;
`valnorm` collapses digit runs to `#`; `t2k` is token 2's part before `=`. Per-case key counts are
pinned from the two reference runs; banner must be exactly once at index 0; a line that is not
column-0 clean but whose stripped form starts with a designed verb is `hidden_shape`; missing
`output`/`case`/`verdict`, or an unknown case, is fail-closed.

Two defects found by auditing, both **observations on green data** (not attack-driven):

* **F1 — full-line normalized-byte pinning is unusable.** `python3 -c` over run1/run2 with the run
  token `MechanicOneShotTest-\d{8}T\d+Z` normalized to `<RUN>`: **37/554 cases** differ between the
  two green runs. Examples: `tween_flash` `transient_modulate=(0.704,…)` vs `(0.7041,…)`;
  `save_process_writer` `pid=3095002` vs `pid=3166882` and two different run paths. Digit
  collapsing + depth-3 keys absorb exactly these (the `pid=` case is why `valnorm` exists:
  without it the gate false-flagged `descendant_pipe_*` on 3 of 4 runs, see §3).
* **F2 — the `[ N% ] <step>` import-progress family is environment-dependent.** Counts per case:
  `export_readiness` 259 (both r102 runs) vs 271 (both r101-era runs); `export_preset_missing` 85
  vs 89. A strict count pin therefore produces 2 false positives on legitimately green r101-era
  rows. Carve-out: `VOLATILE_KEYS = {"raw/["}` (`mut05_gate.py:17`) = presence-only.

### 6.2 Residuals (explicitly NOT closed by this seat)
* **R2 value-axis hole (measured, n2):** shape keys deliberately ignore numeric values, so a
  tamper that changes only a digit inside an otherwise pinned token stays silent. Value pinning is
  the row's own receipt semantics (e.g. `required_stderr`/`signature` fields), not this gate's.
  Label: inference from n2 + key definition; the class is bounded by §3's zero-FP result.
* **R1 progress-family count:** `raw/[` is presence-only (F2), so extra copies of an
  already-pinned progress-shaped line are not count-checked. A *novel* first token is still caught
  (`unpinned` key → count mismatch vs exp=0).
* Not measured by this seat: whether the same account stays silent on a *fresh, re-executed*
  battery run (no new battery run was made — hard rule 1), and the cost of building the pin inside
  `run_battery.py` (mine is a 186 KB embedded literal; the landing implementation should derive it
  from the same run's frozen reference instead of embedding a blob).
