## 6. Order law + minimal re-run plan

**Order law.** Let `F` = the three fold landings (+§5 repairs), `R` = receipt regeneration (battery or targeted), `C` = allowlist census recompute (`r103-w4-census.py`), `G` = gate replay (`G1`/`W7` style record scan) — all four offline except `R`.
1. `G` (over records of run *k*) is unaffected by `F` appearing before or after it: `G` audits run *k*'s bytes, which `F` does not touch. **Partial order: `G` ∥ `F`.**
2. `G` over the *post-fold* tree's records requires `R` then `C` first: `F → R → C → G`. Skipping `C` makes the allowlist stale (a legitimate new multi-PASS row would be flagged, or an old entry masks a new row's count); skipping `R` makes the round claim "the folded bytes passed" unproven (only §3's 6 rows are covered).
3. `F` must land together with the §5 repairs (same landing), else the tree asserts false byte-identity claims while the receipts were taken from the pre-fold bytes — an unattributable receipt/prose mismatch.
4. `C1` (export_div rows) has no ordering constraint against `G` beyond (2), but its rows are *new* records: they enter the allowlist as 2–3 PASS envelope rows only if their fixtures echo PASS lines (§8's gate counts them as unknown cases until the census is recomputed).

**Minimal re-run plan (cheapest sufficient):** if the orchestrator lands `F` and *does not* re-run the battery, the only runs needed to keep the folded bytes receipt-bearing are the 6 rows in §3 — already taken at `/var/tmp/r103c-V12/out/` (post-fold side, 2 reps each, launch shape verbatim). If the orchestrator re-runs the full battery at close (the r102 precedent), then after `F` do `R` → `C` → `G`; additionally regenerate the 4 seq-family rows' expected-error context is **not** needed (14/14 PASS and the `ERROR: Parameter "t" is null.` allowlist entry are unchanged — that ERROR line is present in both pre/post bytes, see `r100b_seq_clean.*.stderr`).
