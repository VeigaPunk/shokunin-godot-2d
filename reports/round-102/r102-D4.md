## 2. The mismatch is startup latency vs the 0.75 s bound (observation)

**(a) Engine-internal time to script init** — scratch-only probe `/var/tmp/r102-D4/scratch/t0ms.gd`

```
t0ms = 662, 743, 772, 799, 801 ms     (wall 0.735, 0.821, 0.846, 0.875, 0.877 s)
```

**(b) Pipe arrival of the marker** — `bounded_probe.py observe 3.0 -- --delay-clean` (incremental
timestamped read, x from Popen) ×5:

```
header_t = 0.0147, 0.0160, 0.0156, 0.0152, 0.0156
marker_t = 0.7999, 0.6935, 0.6506, 0.6334, 0.6872
```

So the driver's `marker_text in exc.stdout` at a 0.75 s bound asks for an event whose distribution
straddles the bound; the kill follows the `TimeoutExpired` raise by ~10–20 ms, i.e. the effective
deadline is ≈0.76–0.77 s.

**(c) Control — it is engine startup, not corpus content** — minimal `project.godot` (one line
`config_version=5`) + the same t0ms probe, ×3: `t0ms = 786, 810, 663 ms` (wall 0.867, 0.884, 0.738).
Same band ⇒ the corpus/fixture tree is not the cause.

**(d) Historical contrast** [inf] — r26/r29 new-bound arms: `elapsed 1.877–1.888` = 1.5 s delay +
0.38–0.39 s startup; r101: `2.294–2.346` = 1.5 s + 0.79–0.85 s startup. Startup roughly doubled
between the r26 calibration and r101 (host load era; r101-D4 recorded loadavg ≈40).

Refuted sub-hypotheses (each with a measurement, §1/§4):
- "post-kill `communicate()` overwrite discards pre-timeout bytes" — **refuted**: micro-test
  (`python3 /var/tmp/r102-D4/comm_semantics.py`) → `exc.stdout = b'A\n'` (bytes) and second
  `communicate()` returns `'A\n'` (str, *cumulative content*); the driver's line 5350 overwrite keeps
  earlier bytes. The r101 old-arm record showing header-only therefore means the marker bytes truly
  were not in the pipe at kill time.
- "bound drift / harness edit" — **refuted**: constants unchanged since r26
  (`git log -S 'record["marker_observed"]' -- corpus/fixtures/run_battery.py` → 3e44ccb3 only), and
  run_battery.py's last change is ac4eb8d4 (r101, unrelated hunk).
- "host-state pollution (stray processes)" — **refuted** as the mechanism; the census shows no
  interference class (§5); the observed class is CPU/memory-latency of engine startup under load.

## 4. What actually happens at cleanup time (strace, hold arm) (observation)

`bounded_probe.py strace 3.0 out/trace-hold.strace -- --hold-open` (godot is a grandchild; my supervisor
SIGKILLs the godot pid at the bound, exactly mirroring the driver's direct-child kill). The strace
expression used is `-f -tt -T -e trace=process,write,writev,nanosleep,clock_nanosleep` — a full `desc`
class over Godot startup is hundreds of MB; `process` + the write syscalls answer the two questions
(who forks/execs, and when the marker bytes hit fd 1) without that volume:

```
2152921 17:45:04.904493 execve("/usr/bin/godot", ...)
2152975 17:45:04.920656 execve("/bin/sh", ["sh","-c","--","\"xdg-user-dir\" \"DESKTOP\" ...])
2152984 17:45:04.922078 execve("/usr/bin/xdg-user-dir", ...)      -> exited 0 at 04.922530
2152921 17:45:04.932619 write(1, "Godot Engine v4.7.2.stable.arch_"..., 100) = 100   (+0.028 s)
2152921 17:45:06.503432 write(1, "TIMEOUT_PROBE: expected signatur"..., 34) = 34     (+1.599 s)
... (37 thread pids) +++ killed by SIGKILL +++ at 17:45:07.907..09.444               (+3.003 s)
```

- The **only** descendant of the hold-arm process is Godot's own transient `sh -c xdg-user-dir DESKTOP`
  probe (lifetime 16 ms, writes `/home/vgpnk/\n` to the inherited fd 1 — a *real* engine-startup write
  into the captured pipe, pre-script). It is long gone before cleanup; nothing else forks/execs.
- The marker is written by `write(1, …, 34)` — a direct write, not a buffered flush at exit; it is
  visible in the pipe the moment it is written (that is why the bound sweep is a clean threshold).
- 37 threads, all SIGKILLed with the process; no process group is signalled (no `killpg` anywhere; the
  driver calls `process.kill()` on the direct child only).

**Old-arm strace** (`strace 0.75 --delay-clean`): execve `17:44:47.167302`; header `write(1, …, 100)`
at `47.193099`; **no marker write**; `+++ killed by SIGKILL +++` at `47.9175…` (= +0.750 s). The failing
shape reproduced under trace: strace's own overhead pushes startup past 0.75 s, so the arm goes red —
the same mechanism as the loaded r101 runs.

**/proc census during the hold arm** (`bounded_probe.py census 3.0 3.1 -- --hold-open`):

```
t 0.506  State D (disk sleep)  Threads 34  RSS 67072 kB  wchan synchronize_rcu_normal  children []
t 1.013..3.108  State S (sleeping)  Threads 37  RSS 118016 kB  wchan hrtimer_nanosleep  children []
exit -9, pid_alive_post False
```

At cleanup time the descendant story is: **there is no descendant** — the process sleeps on its 30 s
`hrtimer`, zero children, and dies on SIGKILL. `direct_child_alive_after_cleanup=false` is correct.

## 6. Repair / envelope proposal (diff only — no shared file touched)

Recommended (self-calibrating envelope; keeps every constant, adds one arm):
`reports/round-102/mutations/r102-D4-timeout-repair.diff` — a new no-arg `clean_baseline` arm at bound
3.0 measures the startup floor in-run; the marker conjunct becomes conditional:

```python
clean_baseline = bounded_run("clean_baseline", [], timeout_seconds)
marker_requirable = clean_baseline["elapsed_seconds"] < old_timeout_seconds
old_rejects = (old_positive["timed_out"]
               and old_positive["inner_classification"] is False
               and old_positive["direct_child_alive_after_cleanup"] is False
               and (old_positive["marker_observed"] or not marker_requirable))
# payload adds: startup_floor_seconds, marker_requirable, old_marker_within_bound
```

Sound direction: `clean_baseline.elapsed < old_bound` ⇒ startup-to-marker < elapsed < bound ⇒ the
marker clause is satisfiable and stays enforced (r26 discrimination preserved); otherwise the arm
honestly verifies "bound fires, kills the direct child, classifies reject" without demanding an event
the host cannot deliver. Alternatives (`--emit-alt`, `r102-D4-timeout-repair-alts.txt`): (B) drop the
marker conjunct entirely (cheapest, loses the started-script nuance); (C) raise `old_timeout_seconds`
to 1.0 (fragile: measured startup band 0.63–0.88 s leaves ~120 ms margin).

Note for the fold: `probe_timeout` is not a CASES row; it is a meta row whose verdict participates in
the battery roll-up, so the orchestrator can land the envelope without CASES churn.
