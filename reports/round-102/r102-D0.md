`slow_clean_old_bound.marker_observed` requires *(boot + project load + script init) < 0.75 s*.

## §3 Hypotheses eliminated (with the bytes that eliminate them)

  `hold_open_new_bound` is `process.kill()`ed at 3.0 s (`cleanup_exit_code=-9`) and *does* show the

- **H-PIPE-SEMANTICS-CHANGED**: no evidence; the r62 pipe-EOF misattribution surface and its
  `child_exit_at_timeout` discriminator are untouched (the driver's drain behaved identically in 2.4–2.8).
- **H-EXPECTATION-ROT**: refuted — the clause set is unchanged since r26 and the same clause reads

  reading False in both r101 runs; the only difference between the windows is host cost (0.34–0.67 s
  startup then vs 0.79–0.92 s today). Corroborated independently by r102-D4 (recovered r26 PASS receipt)
  and r102-ver6.
- **H-ENGINE-BINARY-CHANGED**: refuted — banner is byte-identical `Godot Engine v4.7.2.stable.arch_linux.ed1daf0bf

Why relative, not a bigger constant: the safe window for the old bound is always
`(marker_arrival, marker_arrival + 1.5 s)` — width 1.5 s, non-empty by construction, but *both* edges
move with the host. A literal (0.75 → 1.25) restores margin only until the next load inflation; the
measurement above shows startup moving 0.38 → 1.18 s across this host's rounds. With `startup_seconds`
taken from the same run, `old_bound = startup + 0.5` sits 0.5 s above the arrival and ≈1.0 s below the
delayed clean exit, and the new bound keeps a full 1.0 s margin (r62's was 1.11 s).

Alternative if the orchestrator refuses new fields: `0.75 → 1.25` and `3.0 → 4.0` (2-token change);
record it as *known-rotting*, not repaired.

`same_script`/`same_expected_exit` stay correct with the control arm (same `res://timeout_probe.gd`,
same `expected_exit=0`), and `bounded_run` already computes `marker_observed`/`inner_classification` on
the clean-exit path (`:5365-5368`), so the control needs no other change.
