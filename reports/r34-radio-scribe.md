## Signal-order caveats requiring raw runtime evidence

- The scout scratch connects after setting A selected, so initial selection should not create a consumer receipt; explicitly assert the initial A=true/B=false state, empty receipts, and initial Label. Do not assume a constructor/default selection signal occurred or erase receipts to hide it.
- When B is selected, the plausible observed sequence is `A:false` followed by `B:true`; selecting A next plausibly yields `B:false` then `A:true`. These are hypotheses, **not verified actual order**. `RadioButton.toggled(bool)` carries each control's new state, and ButtonGroup exclusivity can cause two signals for one selection. Capture both identities and values in raw logs at each action boundary; do not assert order based solely on API intuition or accept unordered membership.
- Scout callbacks set Label to the control name on true and `none` on false. That makes final Label depend on callback order (it ends at the newly selected name only if the true callback is last). Either use this as an intentional order-sensitive observation and prove the sequence, or update Label only on `true` in the fixture; in either case assert exact receipts and Label after each action. Reviewer scratch updates only on true, a distinct consumer behavior.
- Scout assigns `a.button_pressed = true` before adding controls to the tree and connects callbacks later; reviewer does likewise. Thus initial state is programmatically initialized, while the transitions under test must only come from routed focused `ui_accept` input. No manual emits or post-setup state assignment should be used as a substitute.
- **Focus attribution defect in both scratch probes:** each grabs focus on B, then sends the second action while iterating target A without first calling `a.grab_focus()` and asserting A owns GUI focus. Scout's `target` loop variable is only used in printed output; it does not route input to that target. Therefore scratch output, even if later recovered, cannot attribute the second transition to focused A. Re-probe after explicitly focusing/asserting B before the first action and A before the second. The tracked fixture should do likewise.
- Scout's `group.allow_unpress` print is only a property observation; verify the selected pair after each action to demonstrate mutual exclusion. Do not infer exclusivity from only the target becoming selected.
