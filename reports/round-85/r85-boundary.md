## 3. Smoothing **[M]**

- Smoothing **off**: a position write snaps at the next frame (`off_snap=1`).
- Smoothing **on** (speed 5): 11 physics-indexed samples after a 100→200 jump are all **strictly inside**
  (100, 200), **monotone**, and the later samples advance past the first (`final_gt_first=1`), with
  `canvas_transform.origin.x == 32 − center.x` in every sample (`ct_ok=1`). The approach is a plain
  lerp with factor `speed·delta` **[S]** — at this host's idle frame shape (≈175 fps idle) the center is
  still ≈191.8–191.9 after ~50 frames: smoothing is *slow* and idle-frame-shaped, so no absolute value is pinned.
- `reset_smoothing()` snaps **but only from the next frame**: read immediately it still returns the
  smoothed value (113.5023 in exploration 7), one frame later it is exactly the target
  (`reset_center=300.0000,50.0000`, `reset_snap=1`). **[S]** `reset_smoothing()` = `_update_scroll(); smoothed_camera_pos = camera_pos;` — the canvas transform was already written with the old value.
- `force_update_scroll()` **does not snap**: `before_force=306.8239 → force_center=313.1821` (target 400)
  (`force_no_snap=1`, `force_advanced=1`) — it is one extra lerp step. **[S]** it is literally `_update_scroll()`.
- Disabling smoothing mid-approach snaps at the next frame (`off_mid_snap=1`).
- Speed extremes: `0` → frozen (`moved=0`); `−1` → frozen (`moved=0`; the setter clamps to `MAX(0,speed)` **[S]**);
  `0.001` → moves, in range; `5` → moves, in range; `1000` → **out of range** (`inrange=0`: the lerp factor
  `speed·delta > 1` diverges); `1e8` → **NaN** (`nan=1`).
- `process_callback` IDLE vs PHYSICS: both move in range (`pc=[pc1[moved=1 inrange=1]|pc0[moved=1 inrange=1]]`);
  the rate differs because the delta differs (physics uses the physics delta) **[S]**.
- Rotation smoothing (`rotation_smoothing_enabled`, speed 5, 0.0 → 1.0): `grew=1 advanced=1 below=1 exact=0`
  — it moves toward the target and has **not** converged after 30 frames.

## 6. Current-camera arbitration and `enabled=false` mid-frame **[M]**

`cam_current` / `disable_phase`:

| situation | measured |
|---|---|
| no camera in the tree | `get_camera_2d()==null`, ct identity |
| first camera added | **auto-current** (`auto=1`), ct follows it |
| a second camera added | does **not** steal current (`steals=0`) |
| `c2.make_current()` | live: ct = c2's transform |
| current disabled, another enabled camera present | the **first enabled camera in tree order** becomes current, ct reverts to it — but the handover is **deferred**: invisible in the writing callback, landed at the next physics frame (`w1_after` unchanged, `w2 = c2's ct`) |
| re-enable the previously-current camera | does **not** restore it |
| **all** cameras disabled | `get_camera_2d()==null` **and ct resets to identity immediately in the same callback** (`w2_after=(1,0;0,1;0,0)`) |
| re-enable a camera with no current | it becomes current automatically |
| free the current camera | first enabled camera in tree order takes over (ct = its transform) |
| `make_current()` on the other camera in the same callback | live (`e1_after` = the new camera's ct) |
| `visible=false` on the current camera | current status unaffected (exploration) |

**[S]** `set_enabled` → `clear_current()` → `viewport->assign_next_enabled_camera_2d()`;
`_make_current` sets the viewport camera but does not itself rewrite the canvas transform, which is why
the fallback handover is one frame late, while the no-fallback case resets the viewport transform
immediately.

## 7. Zoom degeneracy **[M]**

`zoom_degen` / `zoom_draw`:

- **zoom 0 is refused**, per component: `(0,0)`, `(0,1)`, `(1,0)`, `(-0.0,1)` all emit
  `ERROR: Zoom level must be different from 0 (can be negative).` / `at: set_zoom (scene/2d/camera_2d.cpp:107)`
  and the previous value is kept (`refuse_keeps[read=3.0000,3.0000 …]` after a refused `(0,3)`).
  The same happens through `set("zoom", Vector2.ZERO)`.
- **The refusal threshold is not 0**: `5e-7`, `2e-6`, `5e-6` are refused; `1e-5`, `2e-5`, `1e-4`, `1e-3`
  are accepted (`thr=[z0.0000005[read=3.0000000]…|z0.0000100[read=0.0000100]|…]`) — consistent with the
  source's `Math::is_zero_approx` (≈1e-5) **[S]**.
- Negative zoom is accepted: `(-1,1)` → `(-1,0;0,1;132,-18)`; `(-2,-2)` → `(-2,0;0,-2;232,132)`.
- Huge zoom accepted: `1e12` (float32 `999999995904.0000`) → finite huge ct/wc.
- **`zoom = (INF,1)` is accepted** → `ct=(0,0;0,1;100,18)`, `det=0.0000`, `wc=100.0000,218.0000` —
  a **singular canvas transform is reachable, but only through INF/NAN zoom, never through 0**.
- **`zoom = (NAN,1)` is accepted** → all-NaN ct, `det=-nan`, center `-nan,50.0000`.
- The engine emits `ERROR: Condition "det == 0" is true.` / `at: affine_invert (core/math/transform_2d.cpp:51)`
  when the singular/NaN transform is used (2 occurrences in `zoom_degen`, 6 in `zoom_draw`; total
  `zoom_degen` stderr = 13 refusal errors + 2 `det == 0`).
- **`_draw` still runs** under every degenerate zoom: `base|inf|nan|huge|neg` all `draws=4` in 4 frames,
  with `wc` = `(332,232)`, `(0,168)`, `(-nan,nan)`, `(3.000000095e14,2.000000008e14)`, `(-268,-168)`.
- The Camera2D node's own `scale` does **not** feed the canvas transform (`scale=(0,0)` leaves ct identity,
  no error) — it is not a second singular path.

## 10. `CanvasLayer.layer` extremes and `follow_viewport` per viewport **[M]**

- `layer` is **not clamped**: `-1000, -129, -128, -1, 0, 1, 127, 128, 129, 1000, 2147483647, -2147483648`
  all read back verbatim. Every layer child reads the same `wc=300,200`, `vx=0,0`, `fin=identity` —
  `layer` never enters the transform (render-order metadata only; headless draw order is creation order,
  which the r85 `cl_draworder` cell already pins).
- `follow_viewport_enabled=true` at `layer=1000` works: `fin == ct`; `follow_viewport_scale=0.5` halves
  the basis and leaves the origin; `follow=false` at `layer=-1000` → identity.
- `visible=false` at `layer=2147483647` → `draws=0` (transforms still compute).
- A nested layer at `layer=±128` under an outer layer with `transform=Transform2D(0.5,(10,20))` reads
  `wc=300,200 isolated=1` — nesting isolates the transform at extreme values too.
- `follow_subvp`: a `CanvasLayer` inside a 320×180 `SubViewport` with follow=true takes the
  **SubViewport's** canvas transform (`fin=(1,0;0,1;120,90)` = `sv.canvas_transform`), not the root's,
  and a root follow layer takes the root ct (`(2,0;0,2;-168,-68)`) **while a sub-viewport camera is also
  current** (`sv_cur=1 root_cur=1`). A nested sub-sub viewport gets its own ct (`70,45`). `follow_viewport_scale`
  scales the basis only. Toggling follow is live (`toggle[live=1]`).

| `offset` written in `_physics_process` + `force_update_scroll()` | `332, 322, 312, 302, 292` — same-frame |
| `offset` written **from inside `_draw`** | the writing draw keeps the old value, the next draw sees `307` (`ct_after=(1,0;0,1;7,32)`) |
| `Tween` on `offset` (idle-driven) | 25 draws, `first=332`, `last=292`, `monotone=1` — per-draw interpolated values |

Consequence: an **offset-based** shake is same-frame; a **position-based** shake lags one frame; a
tween-driven shake is smooth per draw. This is the practical face of §2.

## 13. Physics interpolation **[M]**

- The tracked project (`corpus/fixtures/project.godot`) does **not** set
  `physics/common/physics_interpolation` (default false; `interp_off` reads `setting=false`,
  `root_mode=1` = OFF, `cam_mode=0` = INHERIT, `pc=1` = IDLE).
- With the setting true (a scratch project only, `proj_interp/project.godot`):
  - the engine prints `WARNING: Camera2D overridden to physics process mode due to use of physics interpolation.`
    / `at: _update_process_callback (scene/2d/camera_2d.cpp:88)`;
  - the canvas transform becomes **interpolated between physics frames**: the idle-phase origins are
    fractional (`fractional=7`, vs `0` in the control; exploration 6 measured e.g. `12.9932, -11.8504`
    for a 60 px/physics-frame step), and 2 of 2 sampled frames show intra-frame variation
    (`varied_frames=2` vs 1);
  - the cached-write *shape* survives (`write_invisible=1`) but the value an idle observer sees is the
    interpolated one;
  - `cam.process_callback` still **reads** 1 (IDLE) even though the engine overrode it to physics mode —
    the property is not a faithful witness of the internal override;
  - smoothing + interpolation still moves toward the target (`smooth[moved=1 inrange=1]`).

## 16. Cells threatened (what these edges put at risk)

Nothing in this seat's receipts contradicts a pinned value; the threats are **claim-scope** and
**conditional-configuration** threats.

1. **`camera_proc_cam_phase` — claim scope [highest]** The pins (`A.w1[32,32>32,32]`, `B.w1[32,32>12,32]`,
   `C`≡`A`, `D`, `E.o1[sees=32,32]`) only exercise `position` writes and are all reproduced by my
   measurements. The r85 §3 headline *"The camera's canvas transform is a cached value; a CanvasLayer's is
   live"* is **over-broad** (§2): a reader who generalises it to `zoom`/`offset`/`anchor_mode`/
   `ignore_rotation`/limits/drag offsets is wrong — those setters call `_update_scroll()` synchronously.
   The fold's r85 §3.1 model should be re-read as **per-property**.
2. **`camera_proc_cam_comp` — adjacent new fact** `nocam` identity and the five settled states stand.
   New: with a camera present but `enabled=false` on **all** cameras, the viewport ct resets to identity
   in the same callback (§6) — the same identity `cam_comp` pins for "no camera", reached a different way.
3. **`camera_proc_par_layer` / `camera_proc_par_2d` — zoom scope.** `pbgz2 lp=-112 ign=0` stands;
   `ign=1 → -48` and the negative-zoom no-op extend it. `par_2d`'s `with_canvas = ct.origin·scroll_scale`
   is a **zoom-1** law; at zoom 2 the node position is zoom-independent (§11).
4. **`camera_proc_cl_follow` / `camera_proc_vp_subcam` — extended, no conflict.** `follow_viewport` is
   per-viewport (§10), consistent with the per-viewport camera isolation already pinned.
5. **`camera_follow` / `camera_no_follow` (tracked).** Both set `position_smoothing_enabled=false`
   (the default) and call `force_update_scroll()`; safe. **Conditional threat**: if a future cell enables
   smoothing to test it, the `after.distance_to(target) < 0.01` assertion fails — the centre lags by
   design (§3), and `force_update_scroll()` will not rescue it (§3/F6).
6. **`camera_limit` + `camera_top_limit` + `camera_left_limit` + the three `far_*` negatives.** Safe at
   their ±1000/±100000 bounds, but the fixture's `expected_clamp = boundary ∓ viewport_half` formula is
   valid **only for ranges wider than the viewport**; tightening a limit below 64 px silently switches the
   behaviour to the range-midpoint rule (§4), which would make the negative controls pass for the wrong reason.
7. **Every idle-observation pin (`cam_phase` A/D/E, `cl_phase`, `par_phase`) — conditional.** They are
   byte-stable only while `physics/common/physics_interpolation` is off. Turning it on makes the idle-phase
   canvas transform fractional and forces the Camera2D into physics mode with a WARNING line that would
   appear in the row's stderr (§13). The tracked `project.godot` does not set it — keep it that way, or
   re-derive those rows.
8. **`camera_proc_vp_render_indep`** (physics byte-independence) is **not** threatened: every finding here
   is canvas-side.
