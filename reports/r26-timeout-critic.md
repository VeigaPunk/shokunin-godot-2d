The prior baseline is real but narrow: r22's non-author record accepted an immediate normal exit and rejected a 30s hold-open after 0.75s, while critic startup measured 0.394s (~0.356s margin). The delayed fixture must provide evidence beyond that baseline, not merely a larger generic timeout.

## Adversarial false-admit and race checks

1. **Distinct positive conditions:** A wider timeout alone can mask a hung positive command. Positive accept must still require the delayed fixture's clean exit code 0, expected marker, and no timeout/error; it should not accept merely because marker was printed. The delayed mode should deterministically wait a stated duration *before* emitting the signature and then quit, so its delay is causally beyond the old 0.75s bound. Record requested delay, observed marker timing, elapsed time and exit. A measured bound needs headroom above observed delayed clean completion, not just above the requested sleep; otherwise scheduling/compile variance creates false negatives.

2. **Old-bound contrast:** To prove the old 0.75s bound would reject this exact clean slow startup, run the same delayed fixture/arguments with only timeout changed to 0.75s. It must time out with the child still live at the deadline. A timeout/error classifier must remain false even if the marker subsequently appears while cleanup drains output. Capture whether marker was present in `TimeoutExpired` output *before kill* separately from marker present in final drained output. `communicate()` after kill can return the complete stream, so a final-output marker alone does not establish it arrived before the deadline. The clean new-bound run must independently demonstrate marker then exit 0 before its own deadline.

3. **Delayed marker versus pre-timeout signature:** For the hold-open sensitivity arm, preserve the expected signature before the 0.75s deadline and show the process was still running then; preferably retain the pre-cleanup captured stdout and an explicit `marker_observed_at_timeout` field. The timeout arm must remain false with the signature already observed, even when the new longer bound is used. If this arm also delays the marker past the deadline, it does not show that an already-printed signature cannot defeat timeout classification. Conversely, allowing a marker received during post-timeout cleanup to satisfy the marker predicate is acceptable only as ancillary evidence: timeout must unconditionally force reject classification and must not let later output retroactively convert timeout into accept.

4. **Timing race / arbitrary threshold:** Wall-clock scheduling can move an observation across the deadline. Keep a clear gap: measured clean delayed completion comfortably below the new deadline, and hold-open still running comfortably beyond it. Avoid choosing a new timeout exactly at the measured completion or relying on one run at a boundary. Preserve raw monotonic elapsed/timeout values and repeat enough independent paired trials to detect variability; label any miss as adverse rather than retrying it away. The test demonstrates this one bounded delay, not arbitrary slow startups or hangs.

5. **Exit and cleanup bookkeeping:** On timeout, save the timeout-time `actual_exit=None` separately from the eventual kill return code. Require process was live at timeout and direct child is no longer live after bounded `kill`/`communicate`; an early exit with marker, launch error, missing marker, or cleanup timeout must fail meta. The longer timeout increases worst-case runtime before cleanup, so keep it limited to opt-in probe and do not silently change general battery process timeouts. Do not infer descendants were terminated: prior r22 cleanup review observed a detached descendant survive, and this probe only supports direct-child cleanup.

6. **Keep the comparison fair:** Same Godot binary, scratch project, script path/content, arguments except the specific mode and explicit timeout, expected exit, and marker are needed. Record fixture/runner hashes and Godot version in raw artifacts. If old/new runs use different scripts or only compare ordinary startup to a slow variant, the claimed old-bound counterfactual is not demonstrated. No engine/editor or seeded controls changes are needed.
