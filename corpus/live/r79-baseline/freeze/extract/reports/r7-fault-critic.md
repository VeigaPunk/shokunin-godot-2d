# Round 7 fault-classification critique (read-only)

## Review scope
Reviewed the current `corpus/fixtures/run_battery.py` diff and the committed raw verdicts through `corpus/lessons/r6-export-verifier.json`. No files other than this report were changed. No subprocesses or Godot runs were launched.

## Findings

1. **The opt-in fault mode does not exercise the runner's classification.** It executes raw `subprocess.run` calls in a separate branch, hardcodes each injected record's `passed = False`, and then makes the *mode-level* result PASS when selected output substrings are present. Thus the two records saying FAIL are unconditional labels, not observed decisions from `execute()` or a shared production classifier. The timeout case only proves Python raises `TimeoutExpired`; it does not prove the battery records a timeout as a case FAIL. The error case only proves its synthetic text was printed; it does not prove an expected negative with an unrelated diagnostic is rejected. This can give the intended green meta-test while the bug remains.

2. **A broad `ERROR:` ban would break established negatives.** In the r6 raw verdict, `negative_overlap`, `negative_signal`, `negative_transition`, `camera_no_follow`, `ui_signal_disconnected`, `animation_stuck`, `export_preset_missing`, and both mutation controls emit intentional `ERROR:` lines while passing as expected negatives. `negative_transition` also emits Godot's `ERROR: Can't change to a null scene...` before its intentional negative-control assertion. Conversely, positive fixture errors (e.g. missing resource/script errors) should not be accepted merely because some expected text is also present. Any diagnostic policy must be case-specific and tested against the retained 25 cases, not implemented as “reject ERROR everywhere” or “allow ERROR for every expected nonzero exit.”

3. **The ordinary positive path accepts a forged signature.** For non-export cases, it currently classifies a positive as `code == expected_exit and evidence in output`; it does not reject `ERROR:` or `SCRIPT ERROR:` there (the latter only blocks mutant detection / a final script/parse-error guard exists, so actually this guard later sets `passed=False` for SCRIPT ERROR or Parse Error). A normal `ERROR:` beside a positive signature remains accepted. A signature can also be echoed by an unrelated runtime/engine error while the process exits with the expected code. For expected negatives, `detected` is unused except mutation and the ordinary path likewise trusts exit plus substring; there is no proof the signature came from the intended assertion rather than an unrelated diagnostic containing/echoing it.

4. **Existing timeouts are bounded but no runner-level timeout result is validated.** Script/export limits are 8/60 seconds; `TimeoutExpired` becomes `error="TIMEOUT..."`, `code=None`, which should fail the current expected-exit check. The proposed 0.25-second synthetic timeout does not test those production branches, result schema, or parent CLI verdict. Also preserve the subtle output bytes/text handling when asserting timeout diagnostics.

## Falsification cases before claiming calibration improved

- Factor the actual subprocess invocation/classification into a minimal shared helper (or inject the command at the existing execution seam); do not duplicate a test-only classifier. Run the normal case path with a short injected timeout and assert the returned record has `actual_exit: null`, `error` beginning `TIMEOUT`, verdict `FAIL`, and that the top-level fault test fails if any of those assertions are removed. Keep it isolated from the normal seeded CASES.
- Feed the *same negative case classifier* a subprocess result with its exact required signature plus a distinct `ERROR: injected unrelated engine failure`, correct negative exit, and no script/parse error. Require FAIL. Then feed the known-good expected-negative output unchanged and require PASS. Ensure the unrelated text is not itself included in or appended to the signature.
- Forge the expected signature into an unrelated diagnostic or an extra output line while omitting the actual intended assertion; require FAIL. A substring check alone is vulnerable. At minimum, separately reject unapproved diagnostic lines; preferably require an exact, case-owned diagnostic marker/anchored message and expected exit, without accepting a broad prefix that lets arbitrary appended text through.
- Run all 25 unchanged seeded cases after policy changes; compare case names/verdicts to r6. Include `negative_transition` and `export_preset_missing` specifically so intentional engine errors are not mistaken for unrelated faults. Check both positive and negative cases with injected diagnostics.
- Verify time bounds using monotonic elapsed time around the same production timeout helper, plus a finite outer command bound. An internal “FAIL” record is insufficient if fault mode itself hangs or returns overall PASS on malformed/missing results.

## Narrow policy recommendation

Keep per-case expected exit and signature; add explicit allowed diagnostic evidence for the few intended negative ERRORs and distinguish the expected Godot null-scene diagnostic for `negative_transition`. Reject otherwise-unapproved `ERROR:` / `SCRIPT ERROR:` / parse failures and timeouts for both positive and negative cases. Do not infer “expected error” solely from nonzero exit or a signature substring. A shared line-level validator is preferable to blanket exception for all negative cases, but its allow-list must be grounded in the committed raw outputs and then exercised by the legacy 25-case replay. Avoid changing existing expected signatures just to make a broad heuristic pass.

## Verdict
**Not yet demonstrated / hold calibration credit.** The submitted fault-mode approach currently produces false confidence: it tests `subprocess.run` separately and hardcodes inner FAIL labels, rather than falsifying actual runner behavior. This is fixable with a shared classification seam and narrow diagnostic allow rules; no recommendation to loosen or globally reject negative `ERROR:` diagnostics.
