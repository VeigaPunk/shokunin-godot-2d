# Round 10 launch scout (read-only)

## Findings

- `corpus/fixtures/run_battery.py` already stages a disposable project under `corpus/live/runs/<timestamp>/scratch`, copies fixtures, and exports preset `Linux/X11` to `scratch/out/fixture.x86_64` with `godot --headless --path <project> --export-debug "Linux/X11" <path>`. Existing export classification checks `[ DONE ]`, `savepack`, and a nonempty executable, then inventories products and deletes files in `out` before writing its result. It does **not** preserve the executable or attempt to launch it. A launch test must run before cleanup (or use a separate scratch output directory).
- The fixture project currently has no `run/main_scene` in `project.godot`; its only config is app name/features. Existing `scene_a.tscn` has a simple `SceneA` node with `scene_marker.gd` (`@export var marker := ""`), but neither is a finite startup-event probe. Existing export preset is runnable Linux/X11 x86_64, with `export_path` blank; runner supplies an explicit output path. `godot --version` here reports 4.7.2.stable.
- The runner's normal export case and project are fixture-only. Do not launch a stale artifact from `corpus/live/runs`; build and launch within one newly allocated scratch run so positive export and launch refer to the same bytes.

## Safe finite probe design (recommendation; not executed)

1. Use the runner's existing isolated copy or a separate timestamped directory under `corpus/live/runs`. Create a *new scratch-only* minimal scene and script (do not alter fixture inputs): scene root `Node`, script `_ready()` prints a unique exact token such as `R10_STARTUP_EVENT=ready-v1`, then calls `get_tree().quit(0)`. Assign that scene as `application/run/main_scene` in the scratch project's `project.godot`. Ensure the print precedes quit. Keep the token absent from filenames, export logs, and control project's files.
2. Export Linux/X11 x86_64 to a fresh output path as the current runner does, require its existing export markers/artifact nonempty, then launch that exact executable with `--headless` and captured stdout+stderr. Use an external finite subprocess timeout (e.g. 10 seconds); fail on timeout, nonzero exit, or absence of the exact runtime token. A clean return plus token proves the exported executable started and ran the fixture scene event, not merely that export succeeded. Save raw export/launch output, command, exit/timeout and executable hash in a machine-readable scratch result; do not count the export log itself as event evidence.
3. Make a second independent scratch project from the same staged inputs and scene, but remove/omit `application/run/main_scene` (a genuine missing-startup control, rather than only deleting the print call). Export separately and launch it with the identical arguments and deadline. The control assertion must fail the *same* positive launch predicate: token absent. Prefer additionally requiring the known no-main-scene runtime diagnostic/nonzero exit so an unrelated successful early exit cannot masquerade as the intended control; if Godot instead exits zero without a diagnostic, record this as ambiguous and choose a tighter control. The outer test should pass only when positive assertion is true and negative assertion is false. Preserve both raw outputs and distinguish expected control failure from timeout/unexpected crash.
4. Keep both output trees separate and clean only those newly created files after evidence capture. Never delete broad run directories or launch a pre-existing artifact. Optionally first verify both output directories are empty and inventory exact generated filenames; avoid shell glob cleanup.

## Caveats / falsification

- No launch was executed during this scout. The no-main-scene executable's exact exit code and diagnostic are unverified; this is the key feasibility check. A project with a main scene omitted may export successfully but still emit a runtime startup error. Treat export failure of the control as an invalid control, not proof of launch discrimination.
- `--headless` intentionally avoids display-server dependency and demonstrates only one scripted startup event on this Linux/X11 host. It does not establish interactive GUI behavior, visual correctness, production-project launchability, other-platform support, or publishing readiness.
- Build both positive and negative from fresh scratch copies and use a unique token; otherwise copied `.godot` state, stale executables, or duplicated token text could weaken attribution. The current runner copies fixtures and existing export handler deletes products; integration must place launch before deletion or add a separately scoped launch routine without changing seeded fixtures.
