# Round 32 CheckBox coverage critic (read-only)

## Finding
The proposed CheckBox probe can add a genuinely distinct coverage case, provided its assertions establish a user-action-driven state transition and the signal-driven UI effect separately. CheckBox's checked/unchecked state and `toggled(bool)` are not covered by the existing Button activation fixture: Button checks `pressed` receipts and Label updates, but not a persistent checked property or boolean transition sequence. Existing HUD/health disconnected controls do exercise signal wiring generally, so the novelty is specifically stateful CheckBox interaction, not another generic signal-disconnection test.

## Falsification points / acceptance conditions
- **Do not manufacture the event.** Two `ui_accept` press/release pairs, separated by process frames, should be the only toggle stimulus. Do not assign `button_pressed`, call `set_pressed`/`set_pressed_no_signal`, invoke a callback, or manually emit `toggled`; those would make a state/signal claim independent of focused input. Assert initial unchecked state before sending input.
- **Separate state from callback.** In the connected run, observe checked states `[true, false]`, callback boolean receipts `[true, false]`, and the expected Label updates after each completed action (for example `On`, then `Off`). In the disconnected treatment, use the same two actions and assert state still traverses `[true, false]` before failing on absent callback receipts / unchanged Label, with the designated disconnected diagnostic and exit 2. That ordering distinguishes “toggle works, observer is disconnected” from a failed toggle or setup. A disconnected run that exits before its second action does not demonstrate the paired two-toggle contrast.
- **Prove focus and successful setup first.** After adding controls and awaiting a frame, assert CheckBox and Label are in-tree, initial state/text are correct, then `grab_focus()` and verify both `has_focus()` and viewport `gui_get_focus_owner() == checkbox` before input. Avoid allowing setup/focus errors to share the expected disconnected failure signature. Confirm focus remains on the CheckBox around actions (or state clearly if deliberately not asserting that); focus loss/autofocus would confound the input path. As with the existing fixture, this remains a headless synthetic action, not pointer or real-user focus evidence.
- **Don't mistake state for signal.** A changed `button_pressed` alone would not establish `toggled(bool)` delivery; conversely a manually emitted callback would not establish UI action toggling. Retain independent state observations and callback/Label observations. Avoid relying only on `is_connected`, which proves wiring, not emission.
- **Redundancy boundary.** Button already tests focused `ui_accept`, edge sequencing, and signal-to-Label behavior; `ui_signal_hud` and health-gauge fixtures already include disconnected-signal negatives. Keep this as one narrowly scoped CheckBox connected case plus its causal disconnected treatment, not a generic signal matrix or more Button variants. The distinct checked-state transition and its boolean callback are the defensible coverage delta.

## Verdict
No decisive falsification of the proposed coverage claim, conditional on named non-author real-Godot replay proving both actions, focus/setup preconditions, connected `[true,false]` state+callback+Label sequence, and disconnected `[true,false]` state with the intended signal assertion failure. If those conditions are not established (especially if the disconnected run stops after toggle one), classify the contrast as unproven and do not count the added row as coverage. No runtime probe or source edit was performed for this read-only critique.
