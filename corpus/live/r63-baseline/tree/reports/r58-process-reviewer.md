## App-user-data boundary and regression risks

1. `user://` is not under the project scratch path by definition; it resolves in Godot app user data. A run-local absolute `XDG_DATA_HOME` is therefore essential here. Round 57 boundary probe directly observed the default location outside project scratch under `/home/vgpnk/.local/share/godot/app_userdata/...`; its unique app name mitigated collisions but did not make account storage equivalent to scratch.
2. For the declared Round 58 claim, both writer and reader must receive exactly the same absolute `XDG_DATA_HOME`, same copied project path, and same per-run `project.godot` identity. Each path must resolve under this run's `corpus/live/.../<stamp>/xdg-data`, not account app data. Do not change global `XDG_DATA_HOME` for every case: the executor's Round 57 report found that doing so hid installed export templates and altered export behavior. Keep isolation limited to save invocations.
3. Ensure the writer process has exited successfully before launching reader, and capture distinct PIDs/commands, exit statuses, and uncombined stdout/stderr (or equivalent raw per-invocation evidence). The existing `run_process` combines streams and discards the PID; a final paired receipt should record process identity explicitly, rather than infer independence from two script phases. `subprocess.run` is synchronous so ordered cases can enforce exit-before-next-start, but the receipt still needs evidence of the invocations.
4. Reader mode must be read-only with respect to the positive target: no write/open-WRITE, create-if-missing, repair, fallback to another path, or generation of expected data before opening. Compare parsed structured values to fixed expected data. For the missing-file negative, use a distinct never-created filename (or prove file absence immediately before launch); then assert the reader itself rejects it. A wrong-value negative must be established before reader starts and must not mutate the positive save. Do not accept setup failure, timeout, unrelated error, or writer failure as the expected reader rejection.
5. Preserve both prior Round 57 save cases unless deliberate replacement is separately justified and all old 83 classifications replay exactly. If keeping them, new process coverage should be additive and old raw tuple classifications remain unchanged. Recheck output paths and old test classifications in a fresh named non-author seven-flag run. Do not let an early one-process save case seed a file that inadvertently satisfies the independent reader: the writer case must be the sole source for its target in that run, with unique app-data root.
6. Failed or interrupted runs may leave run-local user files. Use unique per-run roots; avoid cleanup outside the named run root and never touch account-level existing saves. `config/name` timestamp uniqueness is useful, but the verified boundary is the actual absolute XDG path, not the app name alone.
